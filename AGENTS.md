# AGENTS.md — hello_llm_translate

## What this is
Example of translating text using Hugging Face Large Language / Marian MT models (e.g. Helsinki-NLP/opus-mt-en-de).

## Stack
- Python 3.13
- Hugging Face `transformers`, `datasets`, `torch`
- Poetry / pip virtual env
- Ollama (local GPU-accelerated LLM server, optional)

## Setup
```bash
huggingface-cli login   # get a token at https://huggingface.co
python3.13 -m venv env
source env/bin/activate
pip install -r requirements.txt
```

## Run
```bash
# From inside the model dir:
cd Helsinki-NLP/opus-mt-en-de/
./main.py
```
The script loads the Marian model/tokenizer, translates a sample English string to German and prints it. CUDA is used when available.

## Local LLM server (Ollama + qwen3 agent)
OpenAI-compatible, **GPU-accelerated** (measured 2026-09 via task 2: `qwen3:14b` at `11%/89% CPU/GPU` — ~11% spills to CPU, so VRAM sits just under the 9.3 GB model + KV cache; `qwen3:32b` at 20.2 GB would split hard or fail to load). Managed through the `./ask.sh` menu (see README). Status of the setup:

- **Host** runs `ollama serve` on port 11434 in **manual `nohup` mode** (PID/log: `./.ollama.pid`, `./.ollama.log`) — observed from task 2 output, not systemd. `ask.sh` prefers systemd when it is actually there (`systemctl is-active ollama`, routing Start/Stop/Status through `systemctl`) and falls back to `nohup` otherwise, so both paths stay supported; task 2 is the authoritative check ("running — systemd service" vs "running — manual (nohup)"). If you switch to systemd, stop the `nohup` copy first or the port stays held.
- **Bind vs client URL** are separate: the server listens on `BIND` (default `0.0.0.0:11434` from `OLLAMA_HOST`, so containers/other hosts can reach it); `HOST` (default `127.0.0.1:11434`) is what status/test/chat probing uses.
- **Model selection**: `MODEL` resolves to `$MODEL` if exported, else the last pick saved in `./.model` (task 10), else default `qwen3:14b-64k`. That is the **only** registered agent — the 2026-09 wire capture showed classic `qwen3*` calls opencode's tools reliably, and every other candidate (`qwen3:8b`/`32b`, deepseek-r1, qwen2.5-coder, deepseek-coder-v2, qwen3-coder, devstral, qwen3.6 coder) was **removed** from the config, menu and presets to keep the tool simple. Task 21 "loads in" the model: activate it in `.model`, ensure the `-64k` variant exists (builds it if missing), then start opencode with it (unlike task 10, which only sets the model). Task 8 and task 21 abort if the active model is not installed, because opencode cannot resolve an uninstalled tag and silently falls back to its own default. Task 11 can still install any raw model name for plain chat; task 4 ensures the active model.
- **`num_ctx` variants are baked, not saved via REPL**: opencode pushes its tool definitions at the END of the prompt, and Ollama's opencode integration doc requires "a context length of 64k or higher", but the classic `qwen3*` models ship with a built-in 40960 window (below that minimum; tool definitions then get truncated and the model denies having tools). So every installed model is used through a **`<name>-64k` variant** produced by `model_ensure()`, which reads the base Modelfile (`ollama show <name> --modelfile`), strips any `num_ctx`/`PARAMETER` lines, appends `PARAMETER num_ctx 65536`, and runs `ollama create <name>-64k` (a plain raw name with no variant falls through to `ollama pull`). This is deterministic and host-REPL-independent — the interactive `ollama run` → `/set parameter num_ctx` → `/save` path is unreliable on some builds (the slash lines get fed to the model as chat) and is NOT used. Raises only, never lowers; an existing variant is never rebuilt. `CTX_FLOOR` (default 65536) is the single knob; `NUM_CTX` overrides the target. Inspect with task 16: built-in window is `ollama show <model>` (grep is case-insensitive — it prints `Context Length` capitalized), the baked override is `ollama show --parameters <model>` (the `context length` line in plain `ollama show` is the GGUF **default**, not the override). Community fix origin: opencode issue #1034.
- **opencode** in this repo uses the local model via `opencode.json` → provider `ollama` registered through `@ai-sdk/openai-compatible` (`baseURL http://127.0.0.1:11434/v1` when run on the host; use the host LAN IP `192.168.43.2` when opencode runs inside another container). All models are registered there with `tool_call: true` and `interleaved: { "field": "reasoning_content" }` — Ollama returns qwen3's reasoning in that field; the `interleaved` value must be a boolean or a `{ "field": ... }` object (a bare string is rejected by opencode's config schema and silently dropped). Task 8 ensures Ollama is up, asks for a project directory (default: current one; `PROJECT` env skips the prompt), verifies a git root (`git rev-parse --show-toplevel`) and offers `git init` if missing, then starts opencode with it. **The launch goes through kitty**: `kitty --single-instance --directory "$proj" <opencode-bin> --model ollama/$MODEL "$proj"` — a new window in the running kitty instance (the flag is `--single-instance`/`-1`; there is no `--single`), so ask.sh keeps its menu instead of being replaced. `KITTY_BIN` resolves the terminal (default `kitty`; a path, or `0`/`none` to stay in the current terminal) and an unresolvable kitty silently falls back to `exec` in the current terminal; menu line 8 prints which one will be used. Tasks 20/22 no longer exist (single-agent simplification); task 21 shares `run_opencode()` and therefore launches the same way; the `oc` launcher (task 15) stays in the current terminal — you are already in one. **Session working directory ≠ launch folder**: `Project.fromDirectory()` walks up for `.git` and sets the session cwd to the git toplevel, so launching in a subfolder gives you the repo root; with no `.git` anywhere it falls back to the hardcoded `worktree: "/"` global project (upstream #15719 / #24694) and the folder is ignored, and a session rooted outside this repo also bypasses this `opencode.json` (only the global `~/.config/opencode` one, which task 12 refreshes, applies there). To reach folders outside the project mid-session: `/add-directory` or `permission.external_directory` in config. opencode config is not hot-reloaded — restart opencode after changing it.
- **Driving opencode with a local (small) model**: keep `temperature` low so the model stops hallucinating tool names — `opencode.json` sets `options.temperature: 0.2`. The session also auto-loads `.opencode/local-model-rules.md` (via `instructions`), which forbids guessing tools, declares that there is NO `explore`, `list`, or `execute` tool, and forbids wrapping calls in `<tool_code>`/`<tool_call>`/`print()` — sub-agents are started with the `task` tool (`subagent_type: "explore"` / `"general"`). Only classic `qwen3*` calls opencode's tools reliably; the CodeAct models (`qwen3.6:35b-a3b`, `qwen3-coder:30b`) were trained to emit their own dialect (`<tool_code>print(bash(...))</tool_code>` or `execute(...)`) and are NOT reliable for opencode agents — that is why they were removed from the menu.
- **Default `qwen3:14b-64k`** (~9 GB) is the opencode agent: dense 14B, thinking-capable, classic Qwen function-calling generation, baked 64k window.
- The base `qwen3*` models emit reasoning tokens first; give `max_tokens >= 256` or replies come back empty. `ask.sh` uses 512 for tests, 1024 for chat.
- Models reply in the language you use; a bare "hello" may come back in Chinese — say "reply in English" to force it.

Verify: `curl -s http://127.0.0.1:11434/v1/chat/completions -H "Content-Type: application/json" -d '{"model":"qwen3:14b-64k","messages":[{"role":"user","content":"Say one word: hello in Thai"}],"max_tokens":512}'`

## Structure
- `main.py` — translation script
- `requirements.txt` — Python dependencies
- `ask.sh` — Ollama server menu, grouped into four sections and 16 numbered tasks + 3 load-in tasks: **server** (1 start, 2 status, 3 stop, 6 install), **chat** (5 test, 7 interactive), **models** (4 ensure active model, 10 switch model — presets + raw name, 11 download/install a model, 13 ensure every installed model has a `<name>-64k` variant via Modelfile bake, 16 context-size report), **opencode** (8 launch, 12 install global opencode setup, 14 show rules in effect, 15 install `oc` launcher, 21 load in `qwen3:14b-64k`), 9 hardware analysis, 0 exit. Task 2 states the server/bind/probe, the active model from `.model`, the `model` key of this repo's `opencode.json[c]`, the installed models, and a `compute (CPU or GPU, per loaded model)` block parsed from `ollama ps` — so it answers "CPU or GPU" (`100% GPU`, `32% CPU/68% GPU`, `48%/52% CPU/GPU`, `100% CPU`). It flags an active or default model that is not installed (opencode then silently falls back to its own default). With no model resident it offers to load the active model briefly (opt-in, default No) and then reports the split, since `ollama ps` only lists loaded models; declining prints the manual one-liner `ollama run <model> hi >/dev/null 2>&1 & sleep 8; ollama ps`. The startup backend is in `journalctl -u ollama | grep -i "library="` under systemd or the same grep in `./.ollama.log` in `nohup` mode, but that wording is not present in every Ollama version, so the `ollama ps` column is the authoritative source. Task 16 prints `MODEL / SIZE / BUILT-IN / NUM_CTX / VERDICT` per model and marks anything whose effective window (saved/`-64k` `num_ctx` if set, else built-in) is under `CTX_FLOOR`, which defaults to 65536 and matches the opencode requirement. The floor is a single `CTX_FLOOR` env knob shared by tasks 13 and 16.
- `opencode.json` — project opencode config (the local agent model `qwen3:14b-64k` at `limit.context: 65536` with `tool_call: true`, `interleaved: { "field": "reasoning_content" }` and `temperature: 0.2`, default `ollama/qwen3:14b-64k`), loads `instructions`; `permission.task` is denied so the local model cannot offload its work to `general`/`explore` subagents — it must call `bash`/`read`/`glob` directly)
- `.opencode/local-model-rules.md` — tool-protocol rules auto-loaded in opencode sessions (exact tool names, no guessing, `task` tool for sub-agents; a plain question gets a plain text answer in any mode, and a plan-mode `<system-reminder>` is read as "no edits", never as "don't answer / ask clarifying questions"); task 12 copies it to `~/.config/opencode/` on the host for global effect
- `show_rules()` (task 14, also printed by task 8 before launch, exposed as `ask.sh --rules [dir]`) — resolves and prints what a given directory actually loads: cwd, git project root (flagging the `/` global-project fallback), the global config's `instructions` + provider/models + default model, each `opencode.json[c]` from cwd up to the project root, and the `AGENTS.md` chain, with `[ok]`/`[MISSING]`/`[none]` markers and line counts. This is the debugging tool for "which rules am I actually in".
- `/rules` (in opencode) — task 12 also writes `~/.config/opencode/commands/rules.md`, a custom command whose template injects `!`ask.sh --rules`` output into the prompt and tells the model to report it verbatim. This is the in-session way to see loaded rules; opencode has no built-in equivalent (`/details` is the closest but only toggles tool output).
- Task 12 (idempotent, re-runnable) merges three things into the host's global `~/.config/opencode/opencode.json[c]`: the rules file into `instructions`, this repo's whole `provider` block (ollama + the model), and its `model` (default `ollama/qwen3:14b-64k`). Needed because a project with no `opencode.json` cannot resolve `ollama/qwen3:14b-64k` — opencode silently falls back to its default model (big-pickle) otherwise. Re-run it after editing `.opencode/local-model-rules.md`.
- `.model` — state: last model picked with task 10 (gitignored)
- `Helsinki-NLP/` — model dir (opus-mt-en-de)
- `deepseek-ai/` — additional model dir
