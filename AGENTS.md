# AGENTS.md — hello_llm_translate

## What this is
Example of translating text using Hugging Face Large Language / Marian MT models (e.g. Helsinki-NLP/opus-mt-en-de).

## Stack
- Python 3.13
- Hugging Face `transformers`, `datasets`, `torch`
- Poetry / pip virtual env
- Ollama (local GPU-accelerated LLM server, optional)

## Setup
```bash
huggingface-cli login   # get a token at https://huggingface.co
python3.13 -m venv env
source env/bin/activate
pip install -r requirements.txt
```

## Run
```bash
# From inside the model dir:
cd Helsinki-NLP/opus-mt-en-de/
./main.py
```
The script loads the Marian model/tokenizer, translates a sample English string to German and prints it. CUDA is used when available.

## Local LLM server (Ollama + qwen3:14b agent)
OpenAI-compatible, **GPU-accelerated** (measured 2026-09 via task 2: `qwen3:14b` at `11%/89% CPU/GPU` — ~11% spills to CPU, so VRAM sits just under the 9.3 GB model + KV cache; `qwen3:32b` at 20.2 GB would split hard or fail to load). Managed through the `./ask.sh` menu (see README). Status of the setup:

- **Host** runs `ollama serve` on port 11434 in **manual `nohup` mode** (PID/log: `./.ollama.pid`, `./.ollama.log`) — observed from task 2 output, not systemd. `ask.sh` prefers systemd when it is actually there (`systemctl is-active ollama`, routing Start/Stop/Status through `systemctl`) and falls back to `nohup` otherwise, so both paths stay supported; task 2 is the authoritative check ("running — systemd service" vs "running — manual (nohup)"). If you switch to systemd, stop the `nohup` copy first or the port stays held.
- **Bind vs client URL** are separate: the server listens on `BIND` (default `0.0.0.0:11434` from `OLLAMA_HOST`, so containers/other hosts can reach it); `HOST` (default `127.0.0.1:11434`) is what status/test/chat probing uses.
- **Model selection**: `MODEL` resolves to `$MODEL` if exported, else the last pick saved in `./.model` (task 10 "Switch local model", or tasks 20-22), else default `qwen3:14b`. Only the three **verified** classic-Qwen3 agent models are registered and offered: `qwen3:8b` (~5 GB), `qwen3:14b` (~9 GB, recommended), `qwen3:32b` (~20 GB, needs ~24 GB free RAM) — the wire capture of 2026-09 showed only classic `qwen3*` calls opencode's tools reliably. The CodeAct models (`qwen3.6:35b-a3b`, `qwen3-coder:30b`) and unverified candidates were removed from `opencode.json` and the presets; task 11 still pulls any raw name if you want one for chat. Tasks 20-22 "load in" a model: activate it in `.model`, offer to pull it if missing, then start opencode with it (unlike task 10, which only sets the model). Task 8 and every load-in task abort if the active model is not installed, because opencode cannot resolve an uninstalled tag and silently falls back to its own default. Task 11 downloads the picked model (and offers to make it active); task 4 pulls the active model only.
- **opencode** in this repo uses the local model via `opencode.json` → provider `ollama` registered through `@ai-sdk/openai-compatible` (`baseURL http://127.0.0.1:11434/v1` when run on the host; use the host LAN IP `192.168.43.2` when opencode runs inside the docker container). All switchable models are registered there with `tool_call: true`; the base `qwen3*` models also use `interleaved: "reasoning_content"` (Ollama returns their reasoning in that field). Task 8 ensures Ollama is up, asks for a project directory (default: current one; `PROJECT` env skips the prompt), verifies a git root (`git rev-parse --show-toplevel`) and offers `git init` if missing, then starts opencode with it. **The launch goes through kitty**: `kitty --single-instance --directory "$proj" <opencode-bin> --model ollama/$MODEL "$proj"` — a new window in the running kitty instance (the flag is `--single-instance`/`-1`; there is no `--single`), so ask.sh keeps its menu instead of being replaced. `KITTY_BIN` resolves the terminal (default `kitty`; a path, or `0`/`none` to stay in the current terminal) and an unresolvable kitty silently falls back to `exec` in the current terminal; menu line 8 prints which one will be used. Tasks 20-22 share `run_opencode()` and therefore launch the same way; the `oc` launcher (task 15) stays in the current terminal — you are already in one. **Session working directory ≠ launch folder**: `Project.fromDirectory()` walks up for `.git` and sets the session cwd to the git toplevel, so launching in a subfolder gives you the repo root; with no `.git` anywhere it falls back to the hardcoded `worktree: "/"` global project (upstream #15719 / #24694) and the folder is ignored. The project uses its own `opencode.json` if present, otherwise the global `~/.config/opencode` one (Ollama is auto-discovered, so the local model works even in a project with no config). To reach folders outside the project mid-session: `/add-directory` or `permission.external_directory` in config; community `opencode-dir` plugin adds a real `/cd`. opencode config is not hot-reloaded — restart opencode after changing it.
- **Driving opencode with a local (small) model**: keep `temperature` low so the model stops hallucinating tool names — `opencode.json` sets `options.temperature: 0.4` on `qwen3.6:35b-a3b` and `qwen3-coder:30b`. The session also auto-loads `.opencode/local-model-rules.md` (via `instructions`), which forbids guessing tools, declares that there is NO `explore`, `list`, or `execute` tool, and forbids wrapping calls in `<tool_code>`/`<tool_call>`/`print()` — sub-agents are started with the `task` tool (`subagent_type: "explore"` / `"general"`). Only CLASSIC qwen3 (`qwen3:14b`, `qwen3:8b`, `qwen3:32b`) calls opencode's tools reliably: the CodeAct models `qwen3.6:35b-a3b` and `qwen3-coder:30b` were trained to emit their own dialect (`<tool_code>print(bash(...))</tool_code>` or `execute(...)`) and are NOT reliable for opencode agents — verified 2026-09 by wire capture (opencode sent correct `tools`; only classic qwen3 completed a real tool call in opencode). Keep them for chat/bulk code, switch back with task 10.
- **Context window (`num_ctx`)** — opencode pushes its tool definitions at the END of the prompt; a too-small window (Ollama default can be 4096) truncates them and the model then denies having tools (e.g. "I cannot execute shell commands"). Ollama's opencode integration doc states opencode "requires a context length of 64k or higher", so the classic `qwen3*` agents are registered with `limit.context: 65536`; `qwen3:14b` ships with 40960 (below that minimum) and must be raised with `NUM_CTX=65536 ./ask.sh` (task 13), which *raises* any model below the floor in place via `ollama run` → `/set parameter num_ctx` → `/save` and never lowers one. Inspect before/after with task 16 (built-in context length is `ollama show <model>`; the saved override is `ollama show --parameters <model>` — both greps are case-insensitive because `ollama show` prints `Context Length` capitalized). Community fix origin: opencode issue #1034.
- **Default `qwen3:14b`** (~9 GB) is the opencode agent: dense 14B, thinking-capable, and the classic Qwen function-calling generation that reliably uses opencode's tools (glob/grep/read/bash). The CodeAct models `qwen3.6:35b-a3b` (~30 GB) and `qwen3-coder:30b` (~19 GB) produce their own tool dialect instead, so they are kept for chat/fast bulk code only.
- The base `qwen3*` models emit reasoning tokens first; give `max_tokens >= 256` or replies come back empty. `ask.sh` uses 512 for tests, 1024 for chat.
- Models reply in the language you use; a bare "hello" may come back in Chinese — say "reply in English" to force it.

Verify: `curl -s http://127.0.0.1:11434/v1/chat/completions -H "Content-Type: application/json" -d '{"model":"qwen3:14b","messages":[{"role":"user","content":"Say one word: hello in Thai"}],"max_tokens":512}'`

## Structure
- `main.py` — translation script
- `requirements.txt` — Python dependencies
- `ask.sh` — Ollama server menu (tasks: 1 start, 2 status, 3 stop, 4 pull active model, 5 test chat, 6 install, 7 interactive chat, 8 opencode in a chosen project dir, 9 hardware analysis, 10 switch local model, 11 download a model, 12 install global opencode setup on the host, 13 raise num_ctx on models below the floor, 14 show rules in effect, 15 install `oc` launcher, 16 context-size report, 20/21/22 load in qwen3:8b / 14b / 32b). Task 2 states the server/bind/probe, the active model from `.model`, the `model` key of this repo's `opencode.json[c]`, the installed models, and a `compute (CPU or GPU, per loaded model)` block parsed from `ollama ps` — so it answers "CPU or GPU" (`100% GPU`, `32% CPU/68% GPU`, `48%/52% CPU/GPU`, `100% CPU`). It flags an active or default model that is not installed (opencode then silently falls back to its own default). With no model resident it offers to load the active model briefly (opt-in, default No) and then reports the split, since `ollama ps` only lists loaded models; declining prints the manual one-liner `ollama run <model> hi >/dev/null 2>&1 & sleep 8; ollama ps`. The startup backend is in `journalctl -u ollama | grep -i "library="` under systemd or the same grep in `./.ollama.log` in `nohup` mode, but that wording is not present in every Ollama version, so the `ollama ps` column is the authoritative source. Task 16 prints `MODEL / SIZE / BUILT-IN / NUM_CTX / VERDICT` per model and marks anything whose effective window (saved `num_ctx` if set, else built-in) is under `CTX_FLOOR`, which defaults to 65536 and matches the opencode requirement. The floor is a single `CTX_FLOOR` env knob shared by tasks 13 and 16.
- `opencode.json` — project opencode config (the 3 verified local agent models `qwen3:8b`/`14b`/`32b`, all at `limit.context: 65536` with `tool_call: true` and low `temperature`, default `ollama/qwen3:14b`, loads `instructions`)
- `.opencode/local-model-rules.md` — tool-protocol rules auto-loaded in opencode sessions (exact tool names, no guessing, `task` tool for sub-agents); task 12 copies it to `~/.config/opencode/` on the host for global effect
- `show_rules()` (task 14, also printed by task 8 before launch, exposed as `ask.sh --rules [dir]`) — resolves and prints what a given directory actually loads: cwd, git project root (flagging the `/` global-project fallback), the global config's `instructions` + provider/models + default model, each `opencode.json[c]` from cwd up to the project root, and the `AGENTS.md` chain, with `[ok]`/`[MISSING]`/`[none]` markers and line counts. This is the debugging tool for "which rules am I actually in".
- `/rules` (in opencode) — task 12 also writes `~/.config/opencode/commands/rules.md`, a custom command whose template injects `!`ask.sh --rules`` output into the prompt and tells the model to report it verbatim. This is the in-session way to see loaded rules; opencode has no built-in equivalent (`/details` is the closest but only toggles tool output).
- Task 12 (idempotent, re-runnable) merges three things into the host's global `~/.config/opencode/opencode.json[c]`: the rules file into `instructions`, this repo's whole `provider` block (ollama + all 3 models), and its `model` (default `ollama/qwen3:14b`). Needed because a project with no `opencode.json` cannot resolve `ollama/qwen3:14b` — opencode silently falls back to its default model (big-pickle) otherwise. Re-run it after editing `.opencode/local-model-rules.md`.
- `.model` — state: last model picked with task 10 (gitignored)
- `Helsinki-NLP/` — model dir (opus-mt-en-de)
- `deepseek-ai/` — additional model dir
